## 🧭 原則（基本従う。状況が変わっていたら再検討を提案）

- ❌ 2026-08-17：**自律エージェントの指示書は「やること」より「止まりどころ」が先**。Codex用 `global/AGENTS.md` に正本巡回・終了時の締め作業・改善提案を書いたら、人間の確認ゲートがないCodexクラウドは全部を毎回実行し、頼んでいない作業で使用量を使い切って本命のビルドが不能になった（のんの報告より）→ 自律実行される指示書には、スコープ上限（依頼されたことだけ）・停止条件（完了したら止まる）・リトライ上限（同じ失敗は2回まで）を必ずセットで書く。Claude Code用の指示は「のんに提示して確認」で自然にブレーキが掛かるが、その構造はCodexには存在しないため、そのまま流用すると暴走設計になる
- ❌ 2026-08-16：**設定リポがあるだけでは全リポ共通設定にならない**。ルートの `AGENTS.md` はそのリポのプロジェクト指示で、他リポを開いたCodexクラウドには届かない。今回、設定リポにはCodex用の入口があったのに人格定義と配布経路がなく、クラウドではガチガチの敬語になった（今セッションで実測）→ 全リポ共通の指示は Codex home の `AGENTS.md` に置き、クラウド環境のセットアップから導入する
- ⭕ 2026-08-16：**設定は「正本・配布・実測」の3点セットで完成**。`codex-kit/global/AGENTS.md` を正本、`setup.sh` を配布、Setup / Maintenance script と新規チャット確認を運用にした。ファイルを作った時点で完了扱いせず、mainマージ後に実際のクラウド環境で口調と指示元を確認する
- ❌ 2026-07-09：**配布の静かな故障**。リポが非公開だったため raw.githubusercontent.com が未認証404を返し、setup.sh の「失敗時は静かにスキップ」設計と重なって、環境の curl 1行が長期間空振りしていた（今セッションで実測確認）→ 配布はリポ公開が前提。「静かに失敗する仕組み」には生存確認の手段をセットで用意する（新セッションで「キット入ってる？」→関西弁で返れば生きてる）
- ⭕ 2026-07-09：**修理は全経路の実地テストで締める**。curl のステータス確認 → setup.sh 本番同様実行 → 中身がv2か検証 → 別リポの新セッションで /kickoff 実測、まで通してから完了宣言した。途中の1点だけ確認して安心しない
- ⭕ 2026-07-09：**矯正より構造で守る**。Web版チャットのモデル挙動（指示無視・メモリ書き換え）は、モデルを躾けるより「正本はGitHub・チャットは触らせない」構造で被害をなくす方が確実だった
- ❌ 2026-08-15：**引っ越しは「移動先」より「参照してる全員」が本番**。Obsidian Vault を OneDrive 外へ移す手順書で、Obsidian の切り替えは1ステップずつ丁寧に書いていたのに、同じ Vault を読み書きする Codex については「旧パスが書いてあれば直す」の一行しかなかった。のんの「Codexもパス変えないといかんの？」で発覚（今セッション）→ 保存場所を変えるときは、作業を書く前に「そこを読み書きしてる人・ツールの一覧」を作る。直し漏れた参照先が旧データに書き込み続けると正本が静かに二重化し、退避用に残した旧フォルダが「消せないフォルダ」に変わる
- ❌ 2026-08-15：**GUIの入力欄は「何を決める欄か」まで説明する**。GitHub Desktop の Create a New Repository は `Local path ＋ Name ＝ 作成されるフォルダ` という仕様。そこを説明せず Name だけ「ハイフンに直して」と案内した結果、`Obsidian Vault\Obsidian Vault` という入れ子の空リポジトリができた。しかも残骸は後から `error: does not have a commit checked out` で自動同期そのものを止める（今セッションで両方発生）→ 画面の項目を指示するときは、その値が何に効くかと検算（`C:\Users\nokok` ＋ `Obsidian Vault` ＝ 目的のフォルダ）をセットで渡す。作り直したときは残骸の片付けまでを1セットにする
- ⭕ 2026-08-15：**のんに任せる破壊的操作は「削除」でなく「移動」で出す**。入れ子フォルダの片付けを、削除ではなくデスクトップへの退避として案内し、その前に中身（`.git` と `.gitattributes` だけ）を目視確認する手順を挟んだ。間違っていても戻せる状態を保てた → 退避 → 確認 → 後日削除の3段で組む。「消してOK」と言い切るのは、ちゃぴが中身を確認できたときだけ
- ⭕ 2026-08-15：**知識カットオフ後の変化は、のんの観測を正として実地確認する**。「Obsidian Git が無くなってた、作者もいない」という報告に対し、記憶で否定せず Web を確認したところ、プラグイン名と作者名が実際に改名されていた（Obsidian Git／Vinzent03 → **Git／Vinzent**。2026-08-15 時点、community.obsidian.md/plugins/obsidian-git で確認）→ ツール名・UI・手順が「無い」と言われたら、まず調べる。ちゃぴの知識は2026-05までで、ツールの改名は普通に起こる
- ⭕ 2026-08-15：**出そうなエラーは先に予告しておく**。「Git本体が無くてコマンドが出ない可能性が高い、そうなったら入れる」と前置きしてから進めたため、実際に起きてものんが止まらず報告だけで先へ進めた → 初心者向け手順では、想定されるエラーと対処をセットで前置きする。エラーは予告されていれば事故ではなく通過点になる
- ⭕ 2026-08-15：**「これも要る？」という素朴な質問は設計の穴のサイン**。のんの確認が手順書の抜けをそのまま突いた。初心者質問として口頭で答えて終わらせず、その場で手順書に反映する（今セッションで setup-obsidian-github.md の Codex 項目を1行→1セクションへ強化）
